# opt2 CI standard (template ci-v9.17)

One Woodpecker pipeline for every opt2 repo. It is an enforced standard, not a convention:
every repo's `.woodpecker/ci.yaml` is a byte-identical copy of `ci/woodpecker/ci.yaml`, and the
`setup` step fails when the copy drifts, when `tealbrick-ci.json` is invalid, or when package rules are broken.

## Enforcement (C56 D1)
- `ci/MIN_TEMPLATE` on platform `main` holds the minimum template ref (now `ci-v9.9`, set by platform#12). From ci-v6 on, `setup` fails when the repo's template is below it (`belowMinimum`), so raising the file forces every repo in `OPT2_REPOS` (`ci/tb-ci.ts`) to re-adopt first. Move it only after every repo is on the new template: a runner older than ci-v9.1 cannot parse a point release.
- Template refs are `ci-vN` or, for a point release, `ci-vN.M` (ci-v9.1 on). They compare as major.minor: `ci-v9` < `ci-v9.1` < `ci-v10`. A runner older than ci-v9.1 cannot parse `ci-vN.M`.
- Repos still on a template older than ci-v6 (which has no such check) are caught by the platform's `template-audit` pipeline (`.woodpecker/template-audit.yaml`, cron `template-audit` or manual; `node ci/tb-ci.ts audit-templates`): it reads `.woodpecker/ci.yaml` of every repo in `OPT2_REPOS` and goes red naming each one below `MIN_TEMPLATE`. A private repo that this runner cannot read (no `TB_PRIVATE_READ_TOKEN`) is skipped there; its own `setup` step enforces the minimum.
- One template for every repo. Kinds: `library`, `service`, `miniapp`, `bridge`, `portal`, `web`, `static` (static site, e.g. the website: node stages + build, no images), `desktop` (TBD: `paths` = the TypeScript projects, e.g. `["chat"]`), `specs`, `tests`.
- Written exemption, desktop: the macOS/Swift build, signing and notarization cannot run on the Linux CI host. They run on the release Mac (`scripts/release.sh` in opt2-tealbrick-tbd); the release enters the index only through `registry-add-desktop`, which checks the artifact sha256. Secret scan, typecheck, lint, unit and build of the TypeScript parts run in this template like everywhere else. A repo-specific `.woodpecker/*.yml` that repeats these stages (e.g. the old `chat.yml`) must be deleted.

## Stages (in order)

| Step | What it does | Fails when |
|---|---|---|
| secret-scan | gitleaks over the working tree (redacted output) | any finding |
| setup | fetches `tb-ci.ts` at the pinned tag, checks its sha256, template drift, `tealbrick-ci.json`, package rules | drift, bad config, `private` missing, required script missing, no lockfile, any `VOLUME` instruction in any Dockerfile (C42) |
| install | `pnpm install --frozen-lockfile` (or `npm ci`) per path | lockfile out of date |
| osv-scan, osv-check (ci-v9.14, C262) | beside `install`, after `setup`; no secret. `osv-scan` runs osv-scanner v2.6.0 (image pinned by digest) on the pnpm/npm lockfiles that `setup` listed in `.tb-ci/osv-lockfiles` and writes `.tb-ci/osv.json`; `osv-check` judges the report (see "Vulnerability scan" below). `pre-release`, and so `image-check` and `release-record`, wait for `osv-check` | osv.dev unreachable or a lockfile unreadable (the scan step fails, never passes quietly); a HIGH or CRITICAL vulnerability (CVSS >= 7.0; unknown severity counts as HIGH) with no valid `osvIgnore` entry; an expired `osvIgnore` entry or one that ends more than 90 days ahead |
| typecheck / lint / unit | root scripts `typecheck`, `lint`, `test` | non-zero exit |
| conformance | root script `conformance` (required for kind miniapp, bridge) | non-zero exit |
| build | root script `build` if present; writes `.tb-ci/images.sh` | non-zero exit |
| gen | (BSA-03) if a `gen/` is committed: `tb-gen check` first (stale = fail); then the repo's `gen` script (must be `tb-gen all`) and a check that gen/openapi, gen/kit/<product>-kit, gen/docs, gen/railway exist; then `tb-gen check` | kind miniapp without a `gen` script, a stale committed gen/, a gen script that does not produce every kind, drift |
| pre-release (ci-v9.6; boot smoke ci-v9.17) | runs the repo's `preReleaseChecks` (see "Pre-release gate" below); a green no-op without them. Then (ci-v9.17, L68) `boot-smoke`: kind miniapp only, see "Boot smoke" below | a check exits non-zero or its file is missing; the built app does not boot healthy |
| image-check | kaniko builds every declared image, no push (PR, push, manual) | build fails |
| postgres (opt-in, ci-v9.1) | step after `setup` (ci-v9.3: a normal, non-detached step beside the unit step). Starts an ephemeral Postgres 17 only when `tealbrick-ci.json` has `"postgres": true`; otherwise it exits 0 at once (green). When on, the `unit` step waits for it (max 90 s) and gets `TB_TEST_DATABASE_URL`; tests that want a real database skip when it is unset. ci-v9.2: the step stops itself when the unit step ends (see below). ci-v9.3: and it is a normal step, so it is really green | opted in and not reachable within 90 s |
| release-record | tag `v*`: hash-checked runner validates the manifest/services/runtime and prints the release. No token, no signing key; the manifest package is loaded only if it matches `TB_MANIFEST_INTEGRITY` (C62), and `@opt2-tealbrick/spec`, which the manifest package would otherwise pull from a URL without integrity, is pinned by `TB_SPEC_PKG` + `TB_SPEC_INTEGRITY` (sha512). Since ci-v9.9 both tarballs come from the public dist host (`opt2-tealbrick-dist`); the pins in `ci/woodpecker/ci.yaml` are manifest 0.1.12 and spec 0.1.20 (bytes and integrity unchanged by the move) | invalid manifest, version mismatch, any token in the environment |

Paths without `package.json` skip the node stages with a warning (fresh scaffolds stay green).

## Release publishing (C72): GitHub Actions, no personal token
Every releasing repo (images, miniapp kit, or package tarballs) carries `.github/workflows/opt2-release.yml`, a byte-identical copy of `ci/github/opt2-release.yml` (setup fails on drift; `adopt` writes it). It runs on `v*` and `<pkg>-v*` tags only:
1. `build` job — `permissions: contents: read`. Fetches the hash-checked runner, then `tb-ci gh-build`: `docker build` each declared image from the tagged commit with OCI labels (source, revision, version) and saves it to a tarball; builds the miniapp kit (`tb-gen kit --build`), or for a package tag installs, BUILDS (root `build` script, else `pnpm --filter <pkg>... run --if-present build`) and packs the tagged workspace package (`npm pack --ignore-scripts`). Installs use `--frozen-lockfile --ignore-scripts`. No write token exists in this job.
   - Pack guard (ci-v9.1, C75): after `npm pack` the runner reads the tarball and fails if any `main`, `module`, `types`/`typings`, `bin` or `exports` target of the packed `package.json` is missing (for example no `dist/`). ci-v9 packed without a build, so `<pkg>-v*` tarballs released by the ci-v9 workflow can lack `dist/`; re-release them from ci-v9.1.
2. `publish` job — `permissions: packages: write, contents: write`, built-in `GITHUB_TOKEN`. Runs NO repo code: loads the image tarballs, pushes `ghcr.io/<owner>/<image>:<version>` and `:sha-<commit>` (ci-v9.8, C206: `ghcr.io/tealbrick`; a new package is private after its first push, so an org owner makes it public once — the signer reads packages anonymously), prints the digest (information only), attaches kit/package tarballs + `.sha256` to the GitHub release.
Actions are pinned by full commit SHA and limited to the official actions/checkout, setup-node, upload-artifact and download-artifact. Woodpecker keeps every other stage.

## Boot smoke (ci-v9.17, L68)

Unit tests on `src` can pass while `node dist/main.js` crashes (QA-GOV022-1: ERR_MODULE_NOT_FOUND). The `pre-release` step therefore runs a second command, `node .tb-ci/tb-ci.ts boot-smoke`, after the repo's `preReleaseChecks`. It needs no secret and does nothing for other kinds (`boot-smoke: not a miniapp; skipped`).

- No rebuild: it uses the `dist/` that the `build` step made; a missing `dist/` or entry fails with a clear message.
- Entry as the image runs it: `package.json` `main` if set, else `dist/main.js`; started as `node <entry>` in each `tealbrick-ci.json` path that holds a `tealbrick.manifest.json`. The child env is exactly `PATH`, `NODE_ENV=production`, `TB_STANDALONE=1`, `TB_DATA_DIR` (a fresh dir under the OS temp dir), `TB_BACKUP_DIR` (`<data>/backup`) and `TB_LOG_LEVEL=warn`. Nothing else, no secret.
- Port: the manifest `runtime.port` as is (each Woodpecker step is its own container). Taken before the start: FAIL `port <n> in use`.
- Pass: `GET http://127.0.0.1:<port><runtime.healthPath>` answers HTTP 200 with a JSON body whose `version` equals `package.json` `version` AND whose `status` is `ok` or `needs_keys`, within 60 s. The SDK failed mode also answers 200 (`status: "failed"` plus a `failure` code), and `restoring` is not done: both fail, and the message names the status and failure code. Then the health path is polled every 250 ms until 5 s after the first healthy answer: every answer must be healthy and the process must stay alive. Last, every non-remote URL of the `<script type="importmap">` in `dist/ui/index.html` (when that file exists) must be an existing file under `dist/ui`.
- The child is stopped on every exit path (SIGTERM, SIGKILL after 5 s). On a failure the last 40 lines of its stdout+stderr are printed after a redaction pass (GitHub tokens, Stripe keys, webhook secrets, bearer headers, control sequences), then the step exits 1.
- Opt-out, only in `tealbrick-ci.json`: `"bootSmoke": { "skip": true, "reason": "<at least 10 characters>", "expires": "YYYY-MM-DD" }`. Same rules as `osvIgnore`: `expires` must be after today and at most 90 days ahead; an expired or too-far entry fails the step.

## Release publishing in private repos (ci-v9.10, C222; images ci-v9.11, C232): Woodpecker
GitHub Actions do not start in private repos without billing, and we never pay GitHub (C222). A private repo sets `"releaseOn": "woodpecker"` in `tealbrick-ci.json`; `adopt` then writes `.woodpecker/release.yaml` (byte copy of `ci/woodpecker/release.yaml`, drift-checked by `setup`) and removes `.github/workflows/opt2-release.yml`. `setup` fails unless exactly one of the two release files exists (one publisher per tag), and the Actions `gh-build` refuses such a repo. Design and options: `coordination/leads/platform/WOODPECKER-RELEASE.md`.
- Triggers: tags `v*` / `<pkg>-v*`, and a manual pipeline on `main` with the variable `TB_RELEASE_TAG=<existing tag>` (re-release a tag cut before the repo adopted ci-v9.10). Workflow `depends_on: [ci]`: it runs only after the ci workflow is green. The clone step is the default trusted `plugin-git` with `tags: true`.
- `release-build` (no secret): `wp-build` resolves the tag (tag event: must equal the pipeline commit; manual: `main` only, the tag must exist, the tagged commit is checked out), then runs the same build as `gh-build` (install, build, `preReleaseChecks`, pack script or `npm pack`, pack guard). Refuses any token in its environment.
- `release-publish` (repo secret `tb_release_token`, the ONLY step that reads it): a fresh hash-checked runner in `/tmp` (refuses to run inside the workspace; the runner imports `node:` built-ins only) reads `.tb-ci/out` as data, reads the tag's commit from GitHub and requires the plan to match it, then attaches `.sha256`, `.integrity` and the tarball (checksums first: the signer treats a missing tarball as pending). It never creates or moves a tag and never replaces an asset: same bytes = skip, other bytes = red ALARM.
- ci-v9.11 (C232): images. A repo with images may set `releaseOn: woodpecker` (before: refused). Three more steps; the step graph is `release-build` -> `release-image` -> `release-image-push` -> `release-publish` (publish also waits for build):
  - `release-image` (kaniko, the same pinned image as `image-check`, **no secret**): runs the script `wp-build` leaves in `.tb-ci/release-images.sh`: per image `/kaniko/executor --no-push --custom-platform linux/amd64 --tar-path .tb-ci/out/<image>.tar` from the TAGGED commit, with the labels the Actions path sets: `org.opencontainers.image.source=https://github.com/<owner>/<repo>`, `.revision=<tag commit>`, `.version=<version>` (registry-sync's `verifyImageProvenance` checks source + revision). It builds the repo's Dockerfile, so it counts as repo code. No docker daemon, so nothing touches the shared host daemon. Images are built on `v<semver>` tags only (as the Actions path).
  - `release-image-push` (repo secret `tb_ghcr_token` as `GHCR_TOKEN`, the ONLY step that reads it; runs NO repo code): the fresh hash-checked runner in `/tmp` (`wp-push`) checks the plan against the pipeline, reads the OCI labels from each tarball (revision = tag commit, source = this repo; nothing is pushed otherwise), downloads **crane v0.22.1** to a private `/tmp` dir and checks its sha256 (pinned in the runner, which is itself hash-checked), logs in with the token on crane's stdin into a `/tmp` docker config (never argv, never the log, never the workspace; the dir is deleted at the end), and pushes `ghcr.io/<owner lower>/<image>:<version>`. **It refuses to overwrite a tag**: an existing tag with another digest is a red ALARM, the same digest is skipped (retry), and an unreadable answer (401/403/5xx) is also red (only a 404 / MANIFEST_UNKNOWN counts as absent). The pushed digest goes to `.tb-ci/out/<image>.digest`. Pushing is by tag only (no `sha-<commit>` tag; the signer pins by digest).
  - `release-publish` also attaches `release-candidate.json` (schema `opt2.release-candidate/v1`, the document the signer derives: repo, tag, commit, `image@digest` per app/bridge image and its services). It reads the declared images from `tealbrick-ci.json` at the tag commit on GitHub and the digests from the push step, never from the workspace config.
  - Why a crane binary and not a crane image: the push step needs the runner's checks (plan, labels, no-overwrite rule), which are TypeScript in the node image; a `crane:debug` image has busybox only. The binary is as strong as an image digest pin: one pinned sha256 of the release asset (equal to the release's `checksums.txt`) inside the hash-checked runner.
  - A retry after a partial failure (image pushed, publish red) rebuilds the image with another digest, so the push step refuses: cut the next version (tags are evidence). Brand-new package names: GHCR may answer a first push of a package that does not exist yet with 401/403 on the lookup; the push step then stops red (fail closed). The first push of a new package is made once by hand, or by the Actions path.
- Nothing changes for the signer or the mirror: registry-sync still reads the private release with `TB_PRIVATE_READ_TOKEN`, runs the E1 guard and hashes the bytes itself; the dist mirror copies what the signed index names.

## Release signing (SEC-03, C72)
Product pipelines never see the release signing key and write nothing for the index. The platform repo's `.github/workflows/registry-sync.yml` (GitHub Actions, cron `*/15 * * * *` + manual, `main` only, environment `registry` restricted to `main`, secret `RELEASE_SIGNING_KEY`; also `TB_PRIVATE_READ_TOKEN` for private repos, below) is the only job that holds the key. It runs platform code only; its one dependency, `@opt2-tealbrick/manifest`, is installed from `ops/signer/package-lock.json` (integrity-pinned, `--ignore-scripts`). The signer and the template's `release-record` step use the SAME manifest version and integrity (manifest 0.1.12 with spec 0.1.20, which the signer gets through an npm `overrides` entry in `ops/signer/package.json`; since ci-v9.9 both URLs point at the dist host); a unit test (`ci-v9.2:` in `ci/tb-ci.test.ts`) fails if they drift. To change it: edit `ops/signer/package.json`, `npm install --package-lock-only --ignore-scripts` in `ops/signer`, update `TB_MANIFEST_PKG`/`TB_MANIFEST_INTEGRITY` (and the spec pair) in the template, compare the integrity with `coordination/specs/RELEASES.md`, and dry-run the signer first (verify `registry/index.jws`, re-merge the index unchanged, re-sign with a throw-away key, re-validate every app manifest).

### What the signer indexes
- App and bridge releases: every repo in `OPT2_REPOS` except the CLI repo, newest 50 tags each (`/tags?per_page=50`), tags `v<semver>` only. The signer reads `tealbrick-ci.json` at the tag commit and resolves each declared image's `:<version>` digest in ghcr anonymously (tags without published images stay pending; packages must be PUBLIC). Per image it looks in `ghcr.io/tealbrick` first, then in the legacy namespace `ghcr.io/martin-atrin`.
- `cli` and `package` releases (C174/C181, C206 B6): the CLI repo and every repo named in `DIST_PRODUCTS` (cli, relay, harnesses, and the libraries spec, manifest, miniapp-sdk, conformance, create-tealbrick-miniapp, ui plus the pinned `legacy` bridge-repo tarballs). They are read with `TB_PRIVATE_READ_TOKEN`; the entry points at a tarball on a dist host (`artifact.url` must be `<dist base>/<repo>-<tag>/<file>`), and the signer hashes the downloaded bytes itself. Without the token the source is pending: green run, no entry. `DIST_PRODUCTS` versions below `since` are ignored unless listed in `legacy`.
- Desktop releases: by hand, `registry-add-desktop` (above).
- Reviewed inputs, read from `main`, changed by platform PR only: `registry/offers.json`, `registry/harnesses.json`, `registry/products.json`, `registry/ignored-tags.json`, `registry/promotions.json`.
- `PRIVATE_REPOS` (`ci/tb-ci.ts`) lists every opt2 repo that is private in the org. The signer and the template audit read those with `TB_PRIVATE_READ_TOKEN`; an unreadable repo is a red run naming the missing token scope, not a silent skip (the audit alone skips a private 404 when its runner has no token).

### Checks for each new app/bridge tag
0. E1 release guard (C207, `releaseGuard`): the tag commit is on `main` or a `hotfix/*` branch, has a green Woodpecker status (`ci/woodpecker/push/ci` or `ci/woodpecker/tag/ci`) and, from `PR_REQUIRED_FROM` (2026-10-25), came from a merged PR into `main`/`hotfix/*` (a WARN line before that date). A refused tag turns the run red; a tag that must never be indexed goes into `registry/ignored-tags.json` by PR (`{repo, tag, reason, decision}`). The release Action does not repeat this guard; registry-sync is the gate. The read token needs Commit statuses and Pull requests read for private repos.
1. GTP-01: `registry/products.json` binds each product to one repo and kind; a tag from another repo cannot sign the product. `formerRepos` lets earlier releases under the old owner count as the same repo.
2. the tag points at the commit;
3. the manifest, skill files and bridge runtime are re-read from the repo AT that commit (as data) and `manifestDigest`, `skillsDigest` and the runtime record are re-derived;
4. the service images equal the manifest services that have `build`;
5. every image's OCI labels say `revision = <commit>` and `source = https://github.com/<repo>` (a legacy-owner source label is accepted for the same repo name);
6. then the entry is added and the index signed, committing with the built-in `GITHUB_TOKEN`. Any rejected candidate turns the run red with the reason; the other candidates are still indexed.

### Channels (C207 E4)
A NEW app or bridge tag is indexed on `dev` (`tagChannel`). A `stable` app/bridge record exists only as a recorded promotion in `registry/promotions.json` (soak evidence validated by `validatePromotions` and `promotionReleases`: app 24 h, bridge 48 h, expedited needs an `INC-` incident); the new record copies the dev record's image and manifest digest and carries `promotedFrom`. `mergeIndex` refuses any other new stable app/bridge record. Records that were stable before E4 stay stable. `cli`/`package` entries keep the version rule (`-` in the version = dev). Operator steps: `coordination/practice/PROMOTE-STABLE.md`; fields and rules: `registry/README.md` § "Release guard and channels".

Dev-only products (ci-v9.4; `fleet` added by C208): `DEV_ONLY_PRODUCTS` in `ci/tb-ci.ts` (one list: `sample-gate`, `sample-caller`, `sample-pay`, `sample-mismatch`; `fleet` from C208 until C278) are indexed ONLY on channel `dev`, whatever the tag says (`v0.1.2` of a sample becomes a dev release). `mergeIndex` refuses a stable release of any of them on every path. C113: every release of them carries `devOnly: true` in the signed index (Core never offers or deploys them in a stable workspace); `normalizeDevOnly` re-classified the two stable sample records signed before ci-v9.4 to dev (same ids and digests) and folded the identical dev copies of the same versions into them. The registry commit lists each change.

### Index expiry and renewal
The signed envelope (`registry/index.jws`) carries `iat` and `exp`; `publishIndex` signs with `{ iat: now }` and no `exp`, so the manifest package's default applies: `exp = iat + 180 days` (`registry/README.md`; the committed envelope shows `exp − iat = 15552000` s). Two things renew it, both inside `registry-sync`:
1. every `publishIndex` call signs a fresh envelope: a new release, a promotion, a changed offers/harnesses file, a `DEV_ONLY_PRODUCTS` or legacy-owner normalisation, `registry-add-desktop`, `registry-sign`;
2. when none of those is due, `registry-sync` still re-publishes if the committed envelope's `exp` is less than 30 days away (`expiring`, commit message `registry: re-publish`). `publishIndex` runs before the run fails on rejected candidates, so a red run still renews.

So no extra scheduled re-sign is needed as long as `registry-sync` keeps running on its cron and `RELEASE_SIGNING_KEY` is valid. Nothing in this repo alerts on `exp` (the status service has no such check); if the workflow stops (schedule disabled, secret or environment removed), the envelope lapses at its `exp` and `registry-sync` then has to be dispatched by hand (`gh workflow run registry-sync -R Tealbrick/opt2-tealbrick-platform`) or `node ci/tb-ci.ts registry-sign` run with the key. An expired envelope means no new releases are accepted; existing Core rows stay.

## Dependency integrity (S3/C59, C62/BSD-10)
- Every GitHub-release tarball in a lockfile carries `integrity` IN THE LOCKFILE, so pnpm/npm verify it on every install, also inside Docker builds. npm lockfiles have it; for pnpm run `node ci/tb-ci.ts pin-tarballs ../opt2-tealbrick-<name>` after each dependency change: it writes `resolution: {integrity: sha512-…, tarball: …}` into `pnpm-lock.yaml` (pnpm keeps it and fails with ERR_PNPM_TARBALL_INTEGRITY on a mismatch). Setup downloads each tarball and fails if integrity is missing or wrong. `tealbrick-integrity.json` is retired.
- `packageManager` is hash-pinned: `"pnpm@<version>+sha512.<hex>"` (corepack verifies the pnpm download). `corepack use pnpm@9.15.4` writes it.
- Installs never run install scripts: CI uses `pnpm install --frozen-lockfile --ignore-scripts` / `npm ci --ignore-scripts`; setup fails on any Dockerfile `RUN` with `pnpm install` lacking `--frozen-lockfile` or `--ignore-scripts`, or `npm ci` lacking `--ignore-scripts`, or `npm install`.

## Package rules (enforced by setup)
- Every `package.json` (root and workspace packages) has `"private": true` and no `publishConfig` (no npm publishing in opt2).
- Dependencies on `@opt2-tealbrick/*` are either `workspace:*` (package in the same repo) or a release tarball URL, which setup checks exists: a GitHub release of an opt2 repo (either owner) or, since ci-v9.6, a tarball on a platform dist host (`DIST_BASES`, layout `<base>/<repo>-<pkg>-v<ver>/<file>.tgz`; see "Dist host"):
  `"@opt2-tealbrick/manifest": "https://github.com/Tealbrick/opt2-tealbrick-sdk/releases/download/manifest-v0.1.0/opt2-tealbrick-manifest-0.1.0.tgz"` (pins made before C206 name the old owner Martin-Atrin; they stay valid, GitHub redirects the download and the lockfile integrity is unchanged). A registry version string fails.
- v1 package names (`tealbrick`, `@tealbrick/*`) fail the build.
- A committed lockfile. With pnpm: `"packageManager": "pnpm@<version>"` (CI uses corepack on Node 24).
- Root scripts: `typecheck`, `lint`, `test`; plus `conformance` for miniapps and the bridge; plus `gen` (`tb-gen all`, with `gen/` git-ignored) for miniapps; plus `build` in multi-package repos (`pnpm-workspace.yaml`, packages under `packages/<name>/`, shipped compiled as `dist/`). Recommended: `tsc --noEmit`, `biome check .`, `node --test`.
- TypeScript only (Node 24 type stripping: no enums, no parameter properties, `.ts` import extensions).

## Adopt in a repo
```sh
cd <workspace>/opt2-tealbrick-platform
node ci/tb-ci.ts adopt ../opt2-tealbrick-<name> --kind <library|service|miniapp|bridge|portal|web|desktop|specs|tests>
# then edit ../opt2-tealbrick-<name>/tealbrick-ci.json (images, paths) and commit
```
`adopt` copies the template, deletes the baseline `.woodpecker/secret-scan.yaml` (the template has the step), creates `tealbrick-ci.json`, and git-ignores `.tb-ci/`.
Repo-specific extra workflows (for example a macOS job) are allowed as other files in `.woodpecker/`; they must not repeat the standard stages.

## tealbrick-ci.json
Schema: `ci/tealbrick-ci.schema.json`. Example for a miniapp:
```json
{
  "kind": "miniapp",
  "images": [{ "name": "opt2-tealbrick-knowledge", "product": "knowledge", "kind": "app", "manifest": "tealbrick.manifest.json" }]
}
```
Image names are the repo name or `<repo>-<component>` (for example `opt2-tealbrick-bridge-server`).
Optional `"postgres": true` (ci-v9.1) starts the test database step; leave it out when no test reads `TB_TEST_DATABASE_URL`.
ci-v9.2 (was a known red step in ci-v9.1): the detached `postgres` step used to be still running when the pipeline ended, and Woodpecker 3.19 marks such a step red ("no such container") on a green pipeline. Now the runner writes `.tb-ci/postgres-done` when `run test` ends (pass, fail or crash; `setup` clears a stale one), and the step, which runs Postgres in the background instead of `exec`, sees the marker, sends TERM (KILL after 10 s) and exits 0. Only the cleanup ignores an exit status (`wait ... || echo`); a database that never comes up still fails the `unit` step (`waitForTcp`). A 1 h cap stops the step if the unit step never runs. Opted-out repos still get a green "skipped" step.

Apps with companion services (BSA-01): one `kind: "app"` image plus one `kind: "service"` image per manifest `runtime.services[]` entry that has `build` (same `product` as the app, `service` = the manifest service id). Setup fails if they do not match the manifest. On `v*` tags every image is published, and the app's release entry lists `services: [{id, image@sha256}]`.
```json
{ "kind": "miniapp", "images": [
  { "name": "opt2-tealbrick-knowledge", "product": "knowledge", "kind": "app", "manifest": "tealbrick.manifest.json" },
```

## Vulnerability scan (ci-v9.14, C262)
Every pipeline scans the lockfiles (`pnpm-lock.yaml` or `package-lock.json` of every `paths` entry that has a `package.json`) against osv.dev. Nothing else is scanned (no container scan). The `osv-scan` step uses `ghcr.io/google/osv-scanner:v2.6.0@sha256:afd838850ac1a0fcc15ff4a041dc9ba11123c3f0d2666217a5f0fcf9222b55fa` (the image has no node, so the judging is a second step, `osv-check`, in the pinned node image). osv-scanner only sends package names and versions to osv.dev; there is no credential in either step.
`osv-check` takes the CVSS base score of each vulnerability (the report's group `max_severity`, or the advisory label `database_specific.severity` when that is higher). HIGH is >= 7.0 and CRITICAL is >= 9.0; both fail the step. A vulnerability with no usable severity counts as HIGH (fail closed). LOW and MEDIUM are printed only. The table lists id, package@version, severity, the fixed version and the status.
A repo accepts a vulnerability for a limited time in `tealbrick-ci.json`:
```json
"osvIgnore": [{ "id": "GHSA-xxxx-xxxx-xxxx", "reason": "dev-only dependency, not reachable from the product", "expires": "2026-12-01" }]
```
`id` may be the GHSA, CVE or OSV id (any alias of the finding matches). `reason` needs at least 10 characters. `expires` is the first day the entry no longer applies: it must be after the day the check runs and at most 90 days after it. An expired entry, or one that ends more than 90 days ahead, FAILS the check (renew it with a current reason, or fix the dependency). An entry that matches no vulnerability prints a warning (stale; remove it). Unknown keys are refused.

## Dist host for the assets of private repos (ci-v9.6, C154/C157)
A repo that goes private cannot serve its release tarballs from github.com to anonymous consumers. Such a repo sets `"distBaseUrl"` in `tealbrick-ci.json` (or the env `TB_DIST_BASE_URL`, which wins). Only the hosts in `DIST_BASES` (`ci/tb-ci.ts`) are accepted: the assets-only public repo `https://github.com/Tealbrick/opt2-tealbrick-dist/releases/download` (C206), `https://releases.tealbrick.com` for prod. Add a host by platform PR only.
- Layout on a dist host: `<base>/<repo>-<release tag>/<file>`, one path segment. Example: `https://github.com/Tealbrick/opt2-tealbrick-dist/releases/download/opt2-tealbrick-cli-relay-v0.1.0/opt2-tealbrick-relay-0.1.0.tgz` (`.sha256` and `.integrity` sit next to it).
- Release time: `package-pack` rewrites `workspace:` deps to dist URLs instead of the repo's github.com URLs, and checks the dist file exists (so publish the dependency to the dist host before tagging a package that needs it). Without `distBaseUrl` nothing changes.
- Consumers: `setup` accepts a dist URL for `@opt2-tealbrick/*` dependencies (next to the github.com release URL). `pin-tarballs` and the lockfile integrity check cover dist tarballs; the lockfile `integrity` (sha512) is what pins the bytes, whichever host serves them.
- Registry index: `registry-add-desktop --url <dist file> --repo opt2-tealbrick-<name> --sha256 …` (the dist URL is `<base>/<repo>-<tag>/<file>`); the index keeps `artifact.sha256`, which the command downloads and checks. App images stay in public GHCR and need no dist host.
- NOT done by the runner: copying release assets from the (private) source release to the dist host. The release Action's built-in `GITHUB_TOKEN` cannot write to another repo, so the mirror needs its own mechanism (open question for the Coordinator).

## Pre-release gate (ci-v9.6)
`"preReleaseChecks": ["scripts/release-gate.ts"]` in `tealbrick-ci.json` lists repo-relative TypeScript files. The `pre-release` step runs each as `node <file>` from the repo root, in order, on EVERY pipeline (after `gen`), so a green pipeline means the gate passed before anyone tags (L10). The release Action's `gh-build` runs the same list again on the tag: for a package tag after install and build and before `npm pack`, for an `v*` tag after a frozen install and before images are built. The first non-zero exit stops the run; `setup` fails when a listed file does not exist. Checks get `TB_PRE_RELEASE=1`, `TB_RELEASE_TAG` (the tag, empty outside tag runs) and `TB_DIST_BASE_URL` (when a dist base is in force); no tokens are present (the runner refuses `GITHUB_TOKEN`/`GH_TOKEN`/`GHCR_TOKEN`). Use it for repo-specific release rules (for example `opt2-tealbrick-cli`: no dependency on the private bridge, server deny-list) instead of editing the frozen template.

## Package releases (multi-package repos: specs, sdk, bridge, packages)
Tag `<dir>-v<semver>` where `<dir>` is the folder name under `packages/` and `<semver>` equals that package.json `version`
(e.g. `manifest-v0.1.0`). The release workflow installs, runs the build, rewrites in-repo `workspace:` deps to their release URLs
(they must be released first), runs `npm pack`, checks the tarball with the pack guard, and attaches `<name>-<version>.tgz` + `.sha256` to the GitHub release.
Local check before tagging (same path as the Action, no token): `CI_WORKSPACE=$PWD CI_REPO_NAME=<repo> CI_COMMIT_TAG=<dir>-v<ver> CI_COMMIT_SHA=$(git rev-parse HEAD) node <platform>/ci/tb-ci.ts gh-build`, then inspect `.tb-ci/out/assets/*.tgz`.
Asset URL: `https://github.com/Tealbrick/<repo>/releases/download/<dir>-v<ver>/<scope-name>-<ver>.tgz` (`@opt2-tealbrick/x` -> `opt2-tealbrick-x-<ver>.tgz`). With `distBaseUrl` the dependency URLs written into the packed tarball point at the dist host instead (see above).

## App releases
Tag `v<semver>` (no build metadata). Channel from the version: `1.2.3` stable, `-rc.N`/`-beta.N` beta, anything else (`-dev.N`, `-alpha.N`) dev.
Releases are immutable: the same version with another image digest is rejected. See `registry/README.md`.

## Changing the standard (platform maintainers)
1. Edit `ci/tb-ci.ts` and/or `ci/woodpecker/ci.yaml`. For a new version, bump `TB_CI_REF` in the template.
2. `pnpm stamp` (writes the runner sha256 into the template and `.woodpecker/ci.yaml`).
3. Commit and merge by PR, then tag `ci-vN` on the merge commit and push the tag. Never move a published `ci-v*` tag: repos fetch the runner by tag and check its sha256. Re-run `adopt` in each repo (copies the new template).
4. Raise `ci/MIN_TEMPLATE` by a separate PR only after every repo in `OPT2_REPOS` runs the new template (`template-audit` shows it).
